# Orchard Mirror audio: what the device sends, and how it is decoded

Date: 2 August 2026
Status: **Working.** The phone's audio plays through Orchard Mirror, confirmed on device.

## The finding

The paired CoreDevice audio leg carries **Apple AAC-ELD**, not Opus.

`CoreDeviceAudioPlayer` (now removed) launched a GStreamer pipeline declaring
`encoding-name=(string)OPUS` and ran the RTP payload through `opusdec`. The device does not send
Opus. It answers `start-audio-stream` with:

| Field | Value | Meaning |
| --- | --- | --- |
| `RxPayloadType` | 101 | the RTP payload type of this leg |
| `AudioStreamMode` | 8 | Apple AAC-ELD, 48 kHz stereo |

The payload type is the only thing the old pipeline got right, which is precisely why the failure
was quiet: packets matched the caps filter, the pipeline reached `PLAYING`, and every access unit
handed to `opusdec` was AAC-ELD. Audio behind `ORCHARD_MIRROR_AUDIO=1` never worked — it was not
working badly.

## The wire format

- **One RTP payload is exactly one access unit.** No fragmentation, no aggregation, and no
  RFC 3640 AU-header section. The audio leg needs framing and loss accounting, not a depacketizer.
- **480 samples per channel per frame**, 48 kHz stereo — a 10 ms frame, ~100 packets/second.
- **`AudioSpecificConfig` = `F8 E6 50 00`** — not the value the ecosystem publishes; see below.
- **RTCP receiver reports are mandatory.** The device reaps the audio session after roughly twenty
  seconds without them (`RTCPTimeoutInterval`), which is why the leg tracks an extended highest
  sequence number. The agent already sends these.

### The published magic cookie is wrong

pymobiledevice3 hardcodes `F8 E6 40 00` and calls it `AAC_ELD_ASC_48K_STEREO_480`. ADR 0014 §6
repeats that value, having taken it from there. **It declares 512-sample frames, and the device
sends 480.** The differing bit is `frameLengthFlag`, the first bit of ELDSpecificConfig.

Measured three independent ways:

| Evidence | Result |
| --- | --- |
| RTP timestamp stride on the live stream | 480 per packet on a 48 kHz clock |
| libfdk-aac asked to encode each frame length | 480 → `F8E65000`, 512 → `F8E64000` |
| 604 real access units decoded with each cookie | `F8E65000` decodes all; `F8E64000` fails 450 |

pymobiledevice3 gets away with it because it also passes AudioToolbox `mFramesPerPacket = 480`
alongside the cookie, which overrides what the cookie claims. A decoder given only the cookie does
not have that luxury.

This is the kind of detail that produces plausible garbage rather than an error, so the test decodes
the cookie field by field and asserts on **peak amplitude** of decoded audio rather than on a frame
count — a wrong frame length still "succeeds" for a while.

## What is built

| Piece | Where | Tested |
| --- | --- | --- |
| Leg framing, loss and reorder accounting, extended sequence number | `src/Orchard.Mirror.Media/AacEldAudioLeg.cs` | 6 tests, datagrams built from the RFC 3550 field layout |
| Capture of access units to a file | `src/Orchard.Mirror.Media/AacEldAudioCapture.cs` | 2 tests, driven over a real loopback socket |
| AAC-ELD decode | `src/Orchard.Mirror.Audio.Windows/FdkAacEldDecoder.cs` | decodes a recorded stream to audible samples |
| PCM output | `src/Orchard.Mirror.Audio.Windows/WaveOutRenderer.cs` | opens the real default output device |
| The three joined together | `src/Orchard.Mirror.Audio.Windows/PairedAudioPlayer.cs` | confirmed audible on device |

Checked by sabotage: removing the payload-type filter fails two tests, removing the loss accounting
fails two more, and substituting the ecosystem's `F8E64000` cookie fails the decode test with 450 of
604 access units rejected.

Audio is on by default. If libfdk-aac or an output device is missing, the leg is simply not
requested and the screen still mirrors — a missing codec must never stop the picture.
`ORCHARD_MIRROR_AUDIO_CAPTURE=<path>` records raw access units instead of playing them, for decoder
work.

## The decoder is libfdk-aac, which deviates from ADR 0014 §6

**This needs the ADR amended or the decision reversed.** §6 says the AAC-ELD decoder will be
Orchard's own; this uses libfdk-aac through P/Invoke.

The reasoning, for whoever settles it:

- §4's actual requirement is that **the media path carries no copyleft**. libfdk-aac satisfies that
  — it is not GPL or LGPL, unlike FFmpeg and FAAD2, which is why neither of those was used.
- §6's stated premise was that no OS-provided path exists. That remains true; what changed is that a
  non-copyleft library was identified, which §6 did not consider.
- **Patents are unchanged either way.** AAC-ELD sits in the Access Advance pool and the ELD-era
  patents run past the expired AAC-LC ones. Writing the decoder ourselves would not avoid that, so
  the patent question has to be settled for shipping regardless of which decoder is used.
- `FdkAacEldDecoder` exposes nothing of libfdk-aac, so replacing it later is a one-file change.

Packaging note: the DLL is resolved from `ORCHARD_FDK_AAC`, then the application directory, then the
MSYS2 location. A packaged build must ship `libfdk-aac-2.dll` beside the executable.

## Still open

1. **The ADR §6 deviation above**, which is a licensing and patent decision rather than an
   engineering one.
2. **Whether the device would negotiate a different codec.** `media_stream_offer.py`'s bitrate tier
   table carries markers annotated `16=CELT-NB, 4=SILK, 1=opus(?)`. If the device can be talked into
   Opus, the codec question disappears entirely — Opus is royalty-free with irrevocably licensed
   patents. Untested.
3. **Lip-sync.** `WaveOutRenderer` buffers eight 10 ms frames (~80 ms) and drops rather than waits
   when the queue is full. Nothing has measured audio against video yet.
